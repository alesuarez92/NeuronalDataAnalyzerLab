# Rules for delegated agents

Paste or reference this file when delegating work to a sub-agent.

COMMON RULES (read carefully):
- Repo: /home/user/NeuronalDataAnalyzerLab (MATLAB toolbox, R2021a+). No MATLAB here. octave-cli (Octave 8) exists: use `octave-cli --eval "__parse_file__('file.m')"`-style parse checks, and DO run your pure numeric core functions in Octave on synthetic data where Octave-compatible (write quick scratch scripts under /tmp, not in the repo). CI runs real MATLAB later; the lead will commit and check CI.
- Do NOT commit or push. Edit only the files listed as yours; you may create new files where stated.
- First read: docs/UI_STYLE.md, core/UIKit.m, core/UITheme.m, core/DemoData.m, tests/DemoWalkthroughTest.m, and your target files in full, plus `git log -5 -p --stat -- <your files>` to understand recent fixes. Preserve all existing behaviour, bug fixes, public methods and constructors (no-arg, non-blocking; CI smoke tests construct every window).
- Algorithms go in core/ as headless, documented functions/classes (header comment block in the repo's style: what, inputs/outputs, method). Prefer toolbox-free implementations (base MATLAB only) or guard toolbox use with a fallback; state required toolboxes in the header.
- References: when a method comes from the literature, cite it in the header comment ONLY if you are certain of authors, year, title and venue (well-known papers). If unsure, describe the method without a citation and list it in your report as "needs reference". Never invent a citation.
- UI: follow docs/UI_STYLE.md (UIKit cards/buttons/fields/status/busy/alert/styleAxes/emptyAxes; tooltips with units; one updateControls; primary button = next action). Add public, dialog-free methods for every new action so CI can drive them (like the existing loadDemo/runERP/runSorting pattern).
- Demo data: do NOT edit core/DemoData.m. If your features need extra synthetic data, write generator functions in NEW files under core/demo/ (e.g. core/demo/demoXxx.m) returning a struct with a .truth field, deterministic via RandStream('mt19937ar','Seed',...). Report what should be wired into DemoData.
- Tests: add a NEW functiontests file tests/<Area>FeaturesTest.m that checks your core algorithms recover known ground truth on synthetic data (style of tests/DemoDataTest.m / SignalFeaturesTest.m), and a NEW UI walkthrough file tests/<Area>WalkthroughTest.m in the style of tests/DemoWalkthroughTest.m (copy its setupOnce/setup/shot helpers; frames to test-artifacts/screens/walkthrough/<App>_x<NN>_<step>.png) that drives the new features through public methods. Tests must be deterministic and reasonably fast (< ~60 s each file).
- Do NOT edit: apps/HelpApp.m, core/Main.m, core/DemoData.m, core/UIKit.m, core/UITheme.m, tests/AppSmokeTest.m, tests/DemoWalkthroughTest.m, CHANGELOG.md, README.md, website/. Instead, in your report include ready-to-paste Help text for your features: a Quick start addition (numbered steps using the exact button labels), "Demo data: what you should get", and troubleshooting items.
- Final report: files changed/created, new public API (signatures), what each test checks, references cited (full), anything unverified, and `git diff --stat` + list of new files.
