What it is

The first virtual experiment asks a lab-bench question: how much does blood flow in barrel cortex increase after a whisker stimulus, and when does it peak? The student reads how laser Doppler flowmetry (LDF) works, then plans the recording: probe position, stimulus length, number of stimuli, time between them, baseline before the first stimulus and sampling rate. The simulator records it and writes the same kind of file the lab's acquisition software writes. The student then processes that file from scratch in Extract, Process and Average LDF, reports the numbers, and gets feedback.

  1. Learn: plain-language introduction to the question, the technique, what the raw signal looks like and how the experiment is recorded.
  2. Plan: the protocol is drawn as the values change, with the length and size of the recording, or the reason a plan is not possible.
  3. Record: a LabChart-style file (stimulus on channel 6, LDF on channel 8), different for every student name, with no answer inside.
  4. Analyse: in the normal windows, exactly as with lab data.
  5. Report and check: type the numbers, optionally attach the session files saved in Process LDF and Average LDF, and click Check my results.

Open it with the Virtual lab button in the launcher, or from Help → Virtual lab → Try it with demo data.

Walkthrough: the demo student

The feedback

  • Plan: probe position; time between stimuli (blood flow must be back to baseline before the next stimulus: the simulator knows when); number of stimuli, with the precision to expect; sampling rate (at 10 Hz the heartbeat aliases into a false ripple; 1000 Hz works but makes files much larger); baseline before the first stimulus.
  • Processing (when sessions are attached): the window after the stimulus, the baseline window, the filter (a high-pass filter removes the slow blood-flow response itself) and Relative to baseline.
  • Your results: baseline, peak increase (PU and %), time to peak and number of trials, each compared with a careful analysis of the student's own recording, so noise is not held against them. The reference values stay hidden until Show solution, and the submission records that the solution was shown.
  • What was true (after Show solution): the noise-free answer, and how far any analysis of that recording can be expected to be from it.

Every item comes with a plain-language reason, for example “flow needs about 11 s to return to baseline, so responses overlap” or “a window that ends too early puts the peak at the window's end”. Score: OK = 1 point, Check = ½, Fix = 0.

The simulation

Each student name or ID gives a different simulated animal: a baseline of 90–150 PU, a response of 20–40 PU to a 5 s stimulus over the activated barrel (about half at the edge of the barrel, almost none far from it), vasomotion at 0.08–0.14 Hz, a heartbeat at 5–7 Hz, slow drift and noise, and 15% variation from trial to trial. The same name always gives the same animal, and the same plan always gives the same recording.

The model is simplified: responses add up linearly, and there are no movement artefacts or anaesthesia effects. It teaches the method and its pitfalls, not the physiology of a particular animal.

For the demo student the true answer is a peak increase of +38.6 PU (33.6%) at 5.8 s after onset on a 114.7 PU baseline. The walkthrough's analysis of the recording finds +38.7 PU at 5.9 s.

For instructors

Save submission… writes a .navlab.mat file with the student's name, plan, numbers, attached sessions, the number of checks and whether the solution was shown. Grade a folder… grades every submission in a folder and writes virtual_lab_grades.csv: one row per student with the score, their numbers and the reference values. No answer key needs to be distributed: every recording is re-created from the student's name and plan.

The same functions run from scripts: VirtualLab.record, VirtualLab.grade and VirtualLab.gradeFolder in core/VirtualLab.m.
